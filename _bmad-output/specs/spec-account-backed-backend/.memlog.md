- (direction) User selected account-backed backend as the scope; use express because the product PRD already defines the next backend phase.
- (decision) Use account-backed-backend as the stable slug, derived from the PRD's next account-backed backend phase.
- (assumption) The existing API and recipe graph remain the product baseline; account-backed capabilities extend the backend before Android work begins.
- (capability) CAP-1: A person can register a password account and verify its email; success: unverified password accounts cannot sign in and verification credentials are single-use and expiring.
- (capability) CAP-2: A person can sign in or recover password access using the registered method; success: recovery does not disclose account existence, password reset ends existing sessions, and method conflicts identify the registered method without linking accounts.
- (capability) CAP-3: A person can create or access an account with Google; success: the backend verifies the identity credential and handles existing-account conflicts without automatic linking.
- (capability) CAP-4: A person can manage signed-in sessions across devices; success: sign-out and remote termination prevent further token refresh, and reuse of a rotated refresh token ends that session.
- (capability) CAP-5: An account holder can create, update, and remove one rating per recipe; success: repeated rating updates the same record and combined recipe ratings include source and user values without author identity.
- (capability) CAP-6: An account holder can save, remove, and retrieve favorite recipes; success: My Recipes contains saved recipes and account deletion removes favorites.
- (capability) CAP-7: A person can delete their account; success: account, sessions, and favorites are removed while retained ratings are detached from identity and remain anonymous.
- (constraint) Password accounts require verified email; passwords are salted hashes, refresh tokens are hashed, and verification/recovery credentials are single-use, expiring, and attempt-limited.
- (constraint) All endpoints reading or changing account, session, favorite, or rating data require authentication; user-rating identity is never exposed to other users.
- (constraint) Verify imported source-rating scale and available rating counts before finalizing user-rating validation or aggregation.
- (constraint) Define detailed behavior in scoped OpenSpec changes before implementation; complete all account-backed backend capabilities before Android client work.
- (decision) Keep Android client, recommendations, public third-party API, automatic account linking, roles, and written reviews outside this scope.

- (question) How and through which email service should verification and recovery credentials be delivered, and how should links open in the future Android client?
- (question) What API compatibility and versioning guarantees are required for first-party mobile clients?

- (decision by user) User ratings use whole-number stars 1–5; zero is not a valid rating. Combine source and user ratings by pooling individual values and calculating a count-weighted arithmetic mean.
