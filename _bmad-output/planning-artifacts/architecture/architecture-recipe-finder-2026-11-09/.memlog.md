- (decision by user) ADOPTED: Keep recipe and account-backed state in the existing Neo4j database unless a required guarantee cannot be met there. Neo4j uniqueness constraints and ACID managed write transactions are available in the current stack, so no separate store is introduced.
- (constraint) ADOPTED brownfield boundary: HTTP routes depend on application services, which depend on core repository contracts; infrastructure adapters implement those contracts. Account endpoints must not access Neo4j directly.
- (decision) Account state transitions that must be all-or-nothing (credential consumption, refresh rotation, password reset and session revocation, rating upsert, and account deletion) use managed Neo4j write transactions; graph import remains a separate fresh-database operation and must not own or recreate account schema.
- (decision by user) Protected requests must reject access immediately after sign-out, remote termination, or password-reset revocation; validate the referenced session as active, not only the token signature or expiry.
- (decision by user) Use opaque cryptographically random bearer access tokens. Persist only token hashes and authorize protected requests against the active session record so revocation is immediate.
- (decision by user) Use Argon2id for password hashes with at least the OWASP baseline: 19 MiB memory, 2 iterations, and parallelism 1; each password gets an independent salt.
- (decision by user) Provision account uniqueness constraints in a separate idempotent schema/migration step before the API starts; run it after the fresh recipe import so it does not trip the importer’s non-empty-graph guard, and keep it independent of recipe import.
- (constraint) ADOPTED operational envelope: retain the existing single Express API deployment with Neo4j; local/demo Docker Compose and Caddy remain the deployment path, Neo4j stays private, and Resend/Google credentials are runtime configuration. No new service or production-scale commitment is introduced.
- (decision by user) Use opaque cryptographically random refresh tokens, store only their hashes, retain consumed hashes long enough to detect reuse, and revoke the session atomically when any rotated token is presented again.
- (decision by user) ADOPTED: Implement all account-backed capabilities as modules in the existing modular Express API; do not split authentication into a separately deployed service.
- (decision by user) Google account creation must require an explicit unique username after identity verification; never derive it silently from provider profile data.
- (decision) ADOPTED paradigm: a modular monolith using the existing ports-and-adapters direction. HTTP routes and middleware call application services; services depend on core contracts; Neo4j and provider adapters implement outbound ports; index.ts is the composition root.
- (constraint) ADOPTED API boundary: preserve current public recipe routes and error envelopes; protect only personal account/session/rating/favorite routes with session authentication. Validate inputs at HTTP boundaries and keep domain rules out of routes.
- (constraint) ADOPTED provider boundary: expose Resend email delivery and Google ID-token verification behind application ports; persist account/credential state in Neo4j before sending email; do not make provider calls inside Neo4j transactions or trust client-supplied Google identity claims.
- (constraint) ADOPTED rating ownership: preserve individual anonymous source ratings separately from account-owned user ratings; enforce one user rating per account/recipe; aggregate all individual values by count; account deletion removes the ownership link but retains ratings anonymously.
- (version) Reality-checked existing stack: Node.js 22 container, Express 5.3.0, Neo4j JavaScript driver 6.3.0, Neo4j 5.26 Community, TypeScript 6.0.3. Neo4j managed transactions and uniqueness constraints verified in current official manuals.
- (note) Argon2id baseline verified: OWASP recommends at least 19 MiB memory, 2 iterations, and parallelism 1; RFC 9106 defines Argon2. Node package selection remains an implementation-level decision; the PasswordHasher boundary must enforce Argon2id and the baseline.
- (reconciliation) Completed requirements and brownfield fit checks: specified five-attempt credential limits, verified-email sign-in rules, Google email verification behavior, session inventory and idle expiry, rating removal and arithmetic mean, favorite retrieval, local-only dataset handling, graph-coupled import completion, migration gating, readiness checks, and the existing index.ts/app.ts composition split. These are target design requirements; account persistence and schema migration are not implemented.
- (decision by user) Public recipe details remain unauthenticated and may return combined rating aggregates and identity-free individual values; account-specific rating reads and all rating writes require authentication.
- (decision by user) Trust Google email without separate Resend verification only for Google-authoritative Gmail addresses or verified Workspace addresses carrying the hosted-domain claim; other addresses require Resend verification. Use verified Google sub as provider identity.
- (decision by user) Keep one active verification or recovery challenge per account and purpose; resend atomically invalidates the previous code, issues a new code with at most five attempts, and is rate-limited per account and IP.
- (review disposition) Reconciled rubric, technology, and adversarial findings in the spine: clarified target-versus-implemented status; capability bindings and public rating visibility; shared password rules and Google claim verification; atomic conflict, challenge, refresh, reset, deletion, and rating transitions; legacy aggregate behavior; importer recovery, graph-coupled completion, migration ordering, readiness, and environment-specific ingress. Remaining package, exact route, and rate-limit thresholds stay deferred.
- (reconciliation) Clarified public credential entry points: registration, sign-in, verification/resend, recovery/reset, and Google identity flows use their credential proof; active-session checks protect account self-service and other private operations.
